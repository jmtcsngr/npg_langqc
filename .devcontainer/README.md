# npg_langqc devcontainer

This devcontainer runs the full LangQC stack in GitHub Codespaces — two MySQL
databases, the FastAPI backend, the Vue frontend and an Apache proxy — with no
manual setup. There is **no login screen** and **no OIDC handshake**: you are
signed in automatically as a fixed development user. Most of this document
explains that mechanism; [ports](#ports) and
[database access](#accessing-the-databases) are at the end.

## TL;DR

- Open the forwarded **port 8443** ("LangQC app") — the UI loads already
  authenticated as **`dev@example.com`**, and the QC controls (claim, assign a
  state) are enabled.
- To become a different user, change one value (`DEV_OIDC_EMAIL`) and rebuild
  the container.

## How the authentication works

In production, an [`mod_auth_openidc`](https://github.com/OpenIDC/mod_auth_openidc)
Apache proxy authenticates the user against an OIDC provider and then exposes
their identity to the app in **two** ways:

1. **To the backend, as a request header.** Each authorised request carries an
   `oidc_claim_email` header. `lang_qc/util/auth.py` trusts that header and looks
   the email up in the QC database's `user` table — a known user is authorised, an
   unknown one is not.
2. **To the frontend, as a session-info endpoint.** The SPA reads the current
   user from `GET /login-redirect?info=json` (mod_auth_openidc's
   `OIDCInfoHook userinfo`), which returns `{"userinfo": {"email": ...}}`. This is
   what makes the UI say "logged in as …" and **enable the QC controls**.

A real identity provider cannot run against per-Codespace URLs, so this
devcontainer **skips the login and supplies both of those itself**, from a single
configurable identity, `DEV_OIDC_EMAIL` (default `dev@example.com`, set on the
`proxy` service in `docker-compose.yml`).

### 1. The API header (`proxy/000-default.conf`)

```apache
RequestHeader unset oidc_claim_email                        # drop whatever the client sent
RequestHeader set   oidc_claim_email "${DEV_OIDC_EMAIL}"    # inject the trusted dev identity
```

```
browser ──▶ proxy :8443 ──[ oidc_claim_email: dev@example.com ]──▶ backend :8181
               │
               └─ any client-supplied oidc_claim_email is stripped first, so it cannot be spoofed
```

The backend's real, header-based authorisation path runs exactly as in
production — only the OIDC handshake that would populate the header is replaced.

### 2. The UI session-info endpoint

There is no OIDC module here to answer `/login-redirect?info=json`, so the proxy
writes a tiny JSON document at container start and serves it there:

```
{"userinfo": {"email": "<DEV_OIDC_EMAIL>"}}
```

It is generated from the *same* `DEV_OIDC_EMAIL` as the header (see the `proxy`
`command` in `docker-compose.yml`), so the identity the UI shows and the identity
the API enforces can never disagree. Without this the UI would report "not logged
in" and leave the QC controls disabled, even though the API already accepts the
injected header.

## Who you are, and the seeded users

For the injected identity to be *authorised*, the email must exist in the QC
`user` table. `load_fixtures.py` seeds two users during setup:

| Email                 | Purpose                                            |
| --------------------- | -------------------------------------------------- |
| `dev@example.com`     | default dev identity (matches `DEV_OIDC_EMAIL`)    |
| `qc-team@example.com` | a second QC user, for testing multi-user behaviour |

An email that is injected but **not** seeded gets a `403` ("not authorised")
from the backend; a request with **no** header at all gets a `401`.

## Switching the dev user (in the UI)

To use the app as a different **seeded** user:

1. Edit the `proxy` service in `docker-compose.yml` and change `DEV_OIDC_EMAIL`:
   ```yaml
   environment:
     DEV_OIDC_EMAIL: qc-team@example.com
   ```
2. **Rebuild the container** — Command Palette → *Codespaces: Rebuild Container*.
   The proxy's environment and its startup document are fixed when the container
   is created, and the workspace has no Docker CLI to restart a single service, so
   a rebuild is the supported way to pick up the change. Both the header and the
   `/login-redirect` document move together.

## Adding a new authorised user

1. Add the email to `DEV_USERS` in `load_fixtures.py`.
2. Re-seed the QC database (idempotent — only missing users are added):
   ```bash
   python .devcontainer/load_fixtures.py
   ```
3. To sign in as them in the UI, set `DEV_OIDC_EMAIL` to that email and rebuild
   (see above).

## Acting as any user for API testing (no rebuild)

Because the proxy strips the client header, you **cannot** override your
identity through the app — that is the whole point. For quick API testing as an
arbitrary user, call the backend **directly**, bypassing the proxy, and supply
your own header. The backend is reachable as `lang_qc:8181` on the compose
network (and on forwarded port 8181):

```bash
curl -H "oidc_claim_email: qc-team@example.com" \
     http://lang_qc:8181/pacbio/products/<id_product>/qc_assign ...
```

This is a developer escape hatch, not a way in through the app.

## Verifying the mechanism

**UI identity** — the endpoint the login page reads:

```bash
curl -s http://proxy/login-redirect?info=json
# {"userinfo":{"email":"dev@example.com"}}
```

**API authorisation** — send the *same* protected request with a valid-but-
nonexistent product ID, so the HTTP status alone reveals which identity the
backend saw:

```bash
ID=$(python3 -c 'print("a"*32 + "b"*32)')   # 64-hex, valid format, nonexistent well
BODY='{"qc_type":"sequencing","qc_state":"Passed","is_preliminary":true}'

run() {  # label  url  [extra-header]
  local label="$1" url="$2" hdr="$3" args out
  args=(-s -X PUT "$url" -H "Content-Type: application/json" -d "$BODY")
  [ -n "$hdr" ] && args+=(-H "$hdr")
  out="$(curl "${args[@]}" -w $'\n%{http_code}')"
  printf '%-40s -> %s\n' "$label" "$(tail -1 <<<"$out")"
}

run "A via-proxy,  no client header"  "http://proxy/api/pacbio/products/$ID/qc_assign"
run "B via-proxy,  SPOOFED intruder"  "http://proxy/api/pacbio/products/$ID/qc_assign" "oidc_claim_email: intruder@example.com"
run "C direct,     no header"         "http://lang_qc:8181/pacbio/products/$ID/qc_assign"
run "D direct,     SPOOFED intruder"  "http://lang_qc:8181/pacbio/products/$ID/qc_assign" "oidc_claim_email: intruder@example.com"
```

Expected:

| Test  | Request                                 | Code    | Proves                                                        |
| ----- | --------------------------------------- | ------- | ------------------------------------------------------------ |
| **A** | via proxy, no header                    | **404** | `dev@example.com` injected and accepted (a seeded user)      |
| **B** | via proxy, spoofed `intruder@`          | **404** | client header **stripped** — backend saw the dev identity    |
| **C** | direct to backend, no header            | **401** | backend enforces auth; the proxy is the only identity source |
| **D** | direct to backend, spoofed `intruder@`  | **403** | backend *would* honour a raw header                          |

The decisive pair is **B vs D**: the same `intruder@example.com` header yields
**404 through the proxy** (stripped) but **403 direct** (honoured) — the proxy is
the trusted boundary, and clients cannot spoof identity through it.

## Ports

Codespaces forwards these (configured in `devcontainer.json`):

| Port     | What it is          | Notes                                                                                                                                   |
| -------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **8443** | the app — open this | proxy; one origin for `/ui/` and `/api/`. Forwarded as `protocol: http` because 8443 is a conventional HTTPS port and Codespaces would otherwise assume TLS and return 502 |
| 8080     | frontend only       | Vite dev server without `/api` routing — usually not what you want                                                                      |
| 8181     | backend API only    | FastAPI directly, with no identity injected (see [API testing](#acting-as-any-user-for-api-testing-no-rebuild))                          |
| 3306     | MLWH MySQL          | read-only upstream warehouse data                                                                                                       |
| 3307     | QC MySQL            | read-write QC database                                                                                                                  |

Port 8443 opens automatically when the Codespace is created; the rest are
forwarded silently.

## Accessing the databases

Both databases use the credentials `test` / `test` (matching `tests/testdb.ini`,
so the same settings also drive pytest).

- **From inside the compose network** (the workspace terminal, or another
  service) reach them by service name:
  - MLWH — `mlwh_db:3306`, database `mlwarehouse`
  - QC — `qc_db:3307`, database `langqc`
- **From your machine** (e.g. a GUI client) use the forwarded ports on
  `localhost`, which Codespaces tunnels: `localhost:3306` (MLWH) and
  `localhost:3307` (QC).

The SQLAlchemy URLs, as the backend consumes them:

```
mysql+pymysql://test:test@mlwh_db:3306/mlwarehouse
mysql+pymysql://test:test@qc_db:3307/langqc
```

Quick check from the workspace terminal (SQLAlchemy and PyMySQL are already
installed there; a `mysql` client is not):

```bash
python -c "from sqlalchemy import create_engine, text; \
print(create_engine('mysql+pymysql://test:test@qc_db:3307/langqc') \
.connect().execute(text('SHOW TABLES')).scalars().all())"
```

## Scope and caveats

- This bypass exists **only** for the throwaway Codespaces environment. It is not
  wired into any production or deployment path.
- All requests share one identity at a time (whatever `DEV_OIDC_EMAIL` is set to).
  There is no per-session login.
- The proxy speaks plain HTTP; TLS is terminated by the Codespaces edge. See
  `proxy/000-default.conf` and `docker-compose.yml` for the surrounding setup.
